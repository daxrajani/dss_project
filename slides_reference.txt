  SLIDE 3: Implementation Details

  (Solution slide 2 of 3 — prof requires implementation structure diagram)

  Heading: Implementation Structure & Key Algorithms

  Content (left side — text bullets):
  - ETL: crc32(user_session) % 100 maps sessions to device (55/30/15%) and referrer (direct 40%, google 25%, facebook 15%, instagram 8%, email 7%, affiliate
   5%)
  - Sessionization: Window.partitionBy("user_id").orderBy("event_time") → lag() to compute gap → flag gaps > 30min → cumSum for session index → session_id =
   user_id + "_" + idx
  - Attribution: Left join orders with non-direct session_referrers where session_start ≤ order_time and gap ≤ 24hr → row_number() descending picks most
  recent
  - Anomaly Detection: rangeBetween(-7days, -1day) rolling window → avg(), stddev() → z-score = (count - avg) / stddev → flag |z| > 2

  SLIDE 4: Strengths, Limitations & Distributed Concepts

  (Solution slide 3 of 3)

  Heading: Design Decisions & Distributed Systems Concepts

  Content:

  Distributed concepts exercised:
  - Window functions across partitions (sessionization, attribution ranking)
  - Shuffle-heavy joins (orders ⋈ sessions on user_id with time constraints)
  - Broadcast join optimization (eliminate shuffle for small tables)
  - Partition pruning (date-partitioned Parquet for selective I/O)
  - Rolling window aggregations with rangeBetween (anomaly baseline)

  Strengths:
  - Deterministic enrichment (CRC32) ensures reproducibility across runs
  - Single self-contained script for cloud submission (no dependency installs)
  - All 5 stages instrumented with time.time() for precise benchmarking

  Limitations:
  - Device/referrer are synthetic (not real user data) — limits business insight
  - Attribution re-derives sessions instead of reusing Stage 2 output (trades compute for simplicity)
  - Anomaly detection's Window.orderBy() without partition causes single-partition warning for system-level analysis

  SLIDE 8: Lessons Learned

  (Not explicitly required by prof in slides, but uses remaining slide budget and adds value)

  Heading: Lessons Learned

  Content (2-4 concrete, project-specific lessons — as required by the report):

  1. I/O dominates compute at scale. Parquet write time was 33-48% of total pipeline time across all configurations. The ETL write stage alone took 224s on
  5-worker/10GB — more than all compute stages combined. Lesson: optimize serialization (e.g., tune parquet.block.size, use snappy compression) before
  adding more workers.
  2. Optimization must match data characteristics. Key salting (a textbook skew mitigation) made attribution 2.3x slower because the REES46 dataset has low
  key skew (top user = 0.02% of events). Broadcast join was effective because orders table is small relative to sessions. Always profile before optimizing.
  3. Larger datasets parallelize better. The 1GB dataset achieved only 1.03x speedup going from 4→5 workers (diminishing returns — overhead ≈ useful work).
  The 10GB dataset achieved 1.19x for the same step. Lesson: cluster sizing should be proportional to data volume; over-provisioning small datasets wastes
  resources.
  4. Single-script deployment simplifies cloud ops. Packaging all 5 stages into one cloud_pipeline.py (no pip installs, no module imports) eliminated
  dependency issues on Dataproc and made the benchmark fully automated via shell scripts.
